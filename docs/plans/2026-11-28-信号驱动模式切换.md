# 信号驱动模式切换 实施计划（2026-11-28）

给「模式」加一层自动化：监听主机下发的手柄反馈信号（自适应扳机效果、马达震动、触觉
音频），判断玩家现在在干什么，自动切到对应的映射模式；信号消失后再自动切回默认模式。

## 1. 边界：做 / 不做

**做**

- 每个模式（`default` 除外）可以选一个「进入信号」：信号连续出现一段时间 → 自动切到该模式。
- 该模式可以勾选「信号消失后切回默认」：信号连续消失一段时间 → 自动切回 `default`。
- 信号类型固定一组（数据驱动表，新增只需加一行）：
  - `扳机·阻力（开车油门/刹车）`
  - `扳机·射击`
  - `震动（马达）`
  - `触觉震动（音频触觉）`
  - `任意反馈（扳机/震动/触觉）`
- 手动切换（切换键 / 映射页下拉）后，把「当前正热的信号」压住，直到它们冷掉一次，
  避免刚手动切走就被自动切回来。
- 只在**键鼠玩法 + 会话已连接**时判定；判定用的数据仍只读不写实体手柄。

**不做（本轮）**

- 不做屏幕识别 / 不动 Remote Play 视频链路。
- 不做手柄玩法下的自动切换（那种玩法下模式不影响输入，切了也没有意义）。
- 不把每个信号的阈值、去抖时长做成界面可调（先进预设 JSON 的 `auto_hold` /
  `auto_release`，阈值保持具名常量）。
- 不做「按键组合作为信号」这类新证据源（结构上留好扩展点）。

新增一个纯逻辑模块 `ps5kbm/mode_signals.py`（不 import tkinter / hid），便于单测。

## 3. 架构：模块、依赖方向、公开接口

```
mode_signals.py  （纯逻辑：证据收集 + 状态机）
      ▲                      ▲
      │                      │
   app.py               config.py（只借 SIGNALS 表做合法值校验）
      │
 mapping_ui.py（只摆控件，调 app 的方法）
```

- `SignalWatcher`：记录「某个证据最近一次出现的时间」，回答「这个信号现在还热吗」。
- `AutoSwitch`：状态机，输出「要不要切、切到哪、是进入还是退出」。
- `app.py`：三个反馈回调的**闸门前**喂数据；100 ms Tk 定时器调用状态机；切换统一走
  `_switch_mode()`。
- `mapping_ui.py`：模式行下面加一行控件（下拉 + 勾选），`default` 模式置灰。

## 5. 数据与状态

- 默认模式（`default`）= 回退目标，**不允许配信号**（`build_config` 强制为 `none`），
  否则它会和自己打架。
- 状态机只有三个字段有意义：
  - `armed`：**由自动切换切进去的**模式 id。只有它会自动退出。
  - `hot_since[mode_id]`：候选信号连续热的起点（去抖用）。
  - `cold_since`：当前模式信号开始变冷的时刻（退出用）。
  - 另有 `hold_off`：手动切换后被压住的信号集合，冷掉一次即解压。
- 单次 tick 的顺序：先更新去抖计时 → 判进入（按预设里的模式顺序，先到先得）→
  再判退出。进入优先于退出，所以「下车立刻开枪」不会被上一次的退出逻辑拖住。

## 6. 失败与边界

- 配置里出现未知信号 id → 当作 `none`（不崩、不误判）。
- 会话断开 / 换玩法 / 换预设 / 重建映射 → `reset()`，避免陈旧证据跨会话生效。
- 模式被删除 → `armed` 指向的模式不存在时自动清空。
- 三类数据在键鼠玩法下照样会到（主机推的，和本机有没有接手柄无关）：只进判定，
  绝不写实体手柄——`_pad_forward_active()` 闸门位置不变。
- 时间源统一 `time.monotonic()`，测试里直接传 `now`，不 sleep。

## 7. 演进与扩展点

- 新增信号：`SIGNALS` 加一项；如果证据是新的数据类型，再给 `SignalWatcher` 加一个
  `feed_*`。
- 阈值/去抖要进界面时：`auto_hold` / `auto_release` 已经是配置字段，直接接到控件即可。
- 想做「按键组合触发模式」：它与信号无关，属于另一条路（`InputSource` 的全局热键），
  不要塞进本模块。

## 13. 追加（2026-11-28 深夜）：进车判据改为「只看手柄扳机特征」

### 13.1 起因

用户指出：**交互键也是 `f`**，平时互动会连按（`ffff`），上车也会连按（`fffff`），
所以「进车」的验证必须是**手柄发来的上车信号特征**，不能依赖按键。

原实现的判据是「刚按过交互键（10 秒窗口）+ 上一步是步行 + 这一步两侧 `0x21 FF 03`」。
按键虽然不是充分条件（还要求扳机跳变），但它是个**必要条件**，带来三个问题：

1. 按键语义被过度解读：GTA6 里同一个键既上车又开菜单/拾取，连按会反复开窗口；
2. 时间窗口是隐性依赖：进车确认若晚于 10 秒（比如先按了键又绕一圈才上车），就漏判；
3. 「刚上车按两下三角」这种连按场景需要额外的状态机去猜第二次按键的意图（上一轮的
   `_enter_press_at` 补丁），本质是在给一个不可靠的信号打补丁——补丁悬崖。

### 13.2 改法

- **进车**：`classify_trigger_pair(left, right)` 把每一包反馈归成
  步行（两侧 `0x05`）/ 开车（两侧以 `0x21 FF 03` 开头）/ 其它，判定器见到「开车」就确认，
  **完全不看键盘**。分类前先过 `normalize_trigger_block`（`0x05` + 非零参数 = 阻力）。
- **下车**：仍要交互键（驾驶中 `VEHICLE_EXIT_WINDOW_S` 内出现两侧 Off 才算），因为这正是
  车里的真实动作；另外补两条：
  - 按键那一刻主机最后报的就是 Off → 立刻判下车（主机只在变化时下发，那一包可能很久才来）；
  - 两次按键都赶在进车确认之前时，进车照常确认、那帧 Off 不算下车，**再按一次就纠正**。
- 删掉 `VEHICLE_ENTRY_WINDOW_S` / `_enter_deadline` / `_enter_press_at` / `_interact_at`／
  `window_s` 参数：进车不再需要窗口，也就没有「第二次按键要不要转成下车窗口」的补丁。
- `SIGNALS["vehicle_entry"]` 的显示名改为「进入载具（扳机跳变）」，提示语同步；
  `vehicle_key` 的注释改为「只给下车用」。

### 13.3 取舍与已知边界

- **为什么保留「下车要按键」**：车位里静止时也可能收到 Off，纯按扳机特征判下车会在停车时
  来回切。按键是「我要下车」的明确意图，代价只是脚本强制下车（车毁、过场）时停在驾驶模式，
  按一次交互键或切换键即可。
- **为什么不要求「上一步必须是步行」**：连上主机时人可能已经在车里（第一包就是开车特征），
  要求「上一包」会把这种情况判成「没进车」；而「举枪/开镜」那类误判靠「本次会话见过一次
  步行（两侧 Off）」就挡住了，不必卡得那么死。真机上前一包是什么都能从 `载具判定：` 日志
  回溯，如果出现「步行时被误判成开车」，再按日志加更严格的基线。
- **误判兜底**：万一真在步行时被误判进驾驶，按一次交互键即可回默认（见 13.2 第二条）。
