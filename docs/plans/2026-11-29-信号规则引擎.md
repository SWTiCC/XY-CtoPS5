# 信号规则引擎（可编排的条件树）实施计划（2026-11-29）

## 1. 边界：做 / 不做

**做**（本轮 = 第一步：引擎 + 迁移）

- 把「每个模式配一个信号」升级成**规则表**：每条规则 = 条件树 → 目标模式，另有独立的退出条件树。
- 条件树由可拼的节点组成：信号叶子 / 全部满足 / 任一满足 / 非 / 持续 N 秒 / 锁存 / 先后。
- 规则跟**预设**走（一个预设一整套），GTA6 驾驶规则作为预设内容内置。
- 旧配置（`modes.*.auto_signal`、`auto_leave`）**一次性迁移**成等价规则，迁移后不再写回旧字段。
- 行为与现有实现**逐条对齐**（进车锁存、下车要交互键、上车后立刻下车、去抖时长），用测试锁死。

**不做**（本轮）

- 编辑页面（第二步）；本轮界面上只留一行只读摘要。
- 画布拖拽节点图（已确认先做结构化条件树）。
- 计数器 / 统计类节点（「连续震 3 次」这类）——词汇表留了扩展位，但本轮不实现。

## 2. 约束与复用

- 纯逻辑：`signal_rules.py` 不 import tkinter / hid / config，时间一律由调用方传 `now`，可单测。
- 复用现有事实采集：`SignalWatcher` 的 `feed_*` 接口不变，只是把「信号冷热」换成「事实真假」。
- 复用现有判定时机：仍是界面线程 100ms 定时器；`AUTO_SWITCH_TICK_MS` 不动。
- 复用现有日志/诊断：规则命中时把最近 8 帧原始扳机块 hex 写进 `ps5kbm.log`。
- 配置容错沿用现状：不认识的信号 / 坏结构一律丢弃并保底，不让程序起不来。

## 3. 架构：模块、依赖方向、公开接口

```
config.py ──┐
            ├─→ rule_engine.py（规则 + 状态机，纯逻辑）
            │        ↑
            │   signal_rules.py（事实表 + 条件树，纯逻辑，叶子）
app.py ─────┘        ↑
                     │ facts.is_true(fact_id, now)
             mode_signals.py（事实采集：扳机/震动/触觉/交互键 → 真假）

legacy_rules.py（旧配置迁移，一次性；用户配置换完之后可整份删掉）→ config.py
```

- `mode_signals.py`：**事实层**。只回答「某个事实现在真不真」，不知道模式、不知道规则。
- `signal_rules.py`：**条件语言**。事实表 + 条件节点 + 解析/渲染，纯逻辑。
- `rule_engine.py`：**规则层**。`Rule` + 序列化 + `RuleEngine` 状态机；只依赖条件语言。
- `legacy_rules.py`：**迁移层**。旧 `auto_signal` → 等价规则；只被 `config.py` 调用。
- `app.py`：装配层。把两边的回调接起来，把决定落到 `_switch_mode`。
- 依赖只向内：`signal_rules` / `rule_engine` 不认识 Tk，也不认识配置文件的形状。

公开接口（`signal_rules`）：

```python
FACTS: dict[str, dict]                      # 事实表：id → label / hint
parse_condition(raw, default_hold) -> Condition      # 坏结构抛 ValueError
parse_rules(raw_list, hold, delay, rule_prefix) -> list[Rule]
rules_to_dict(rules) -> list[dict]
migrate_legacy_modes(modes_raw, hold, delay) -> list[Rule]   # 旧配置迁移
class RuleEngine:
    __init__(rules, default_mode="default", modes=())
    reset() -> None
    notify_manual_switch(now, facts) -> None
    update(now, current, facts, modes) -> RuleDecision | None
    status(now, facts) -> list[RuleStatus]   # 给界面/诊断用，只读
```

## 4. 契约：JSON 与节点

预设级字段：

```json
"rules": [
  {
    "id": "gta6-driving",
    "label": "GTA6 · 上车 → 驾驶",
    "enabled": true,
    "target": "driving",
    "enter_hold": 0.8,
    "leave_delay": 1.2,
    "enter": { "type": "latch", "set": {...}, "clear": {...} },
    "leave": { "type": "all", "children": [...] }
  }
]
```

节点（`type` 区分）：

| type | 字段 | 语义 |
|---|---|---|
| `fact` | `fact` | 这个事实现在为真 |
| `all` | `children` | 全部为真 |
| `any` | `children` | 任一为真 |
| `not` | `child` | 取反 |
| `hold` | `seconds`, `child` | 子条件连续为真 N 秒 |
| `latch` | `set`, `clear` | 置位后锁住；`clear` 优先，成立即解除 |
| `before` | `first`, `then` | `first` 出现过，之后 `then` 为真 |

事实（叶子）：

| id | 语义 | 类型 |
|---|---|---|
| `trigger.off` | 两侧扳机都是 Off（`0x05` 全零） | 状态（持久） |
| `trigger.vehicle` | 两侧扳机都是开车特征（`0x21 FF 03`） | 状态（持久） |
| `trigger.drive` | 任一侧是阻力 | 状态（持久） |
| `trigger.drive_both` | 两侧都是阻力 | 状态（持久） |
| `trigger.shoot` | 任一侧是射击效果 | 状态（持久） |
| `rumble` | 主机在震 | 事件（0.4 秒） |
| `haptics` | 触觉 PCM 有能量 | 事件（0.4 秒） |
| `interact` | 交互键按过 | 事件（3 秒脉冲） |

**状态 vs 事件**：扳机是主机「当前设成什么」，只在变化时下发，所以按**最后一次上报的值**持久保存；
震动 / 触觉 / 按键是「发生过」，用时间窗口。

规则语义：

- 进入：规则按列表顺序遍历，`enter` 连续为真 `enter_hold` 秒且目标不是当前模式 → 切过去并 arm。
  已经在目标模式里则只 arm，不重复切。
- 退出：只退出「自己 arm 的那条规则」；`leave` 连续为真 `leave_delay` 秒 → 回默认。`leave` 缺省 =
  永不自动退出。
- 手动切换：把当前已成立的规则压住，直到它冷掉一次（避免刚切走又被切回来）。

## 5. 数据与状态

- 事实：`SignalWatcher` 里三份状态——扳机对分类 + 每侧类型（持久）、三个事件时间戳。
- 规则树：节点自己带状态（`hold._since`、`latch._state`、`before._seen`），`reset()` 全清。
  会话断开 / 换玩法 / 换预设 / 换输入模式时清空，避免陈旧状态跨会话生效。
- 配置：`AppConfig.rules`；`ModeConfig` 不再有 `auto_signal` / `auto_leave`。

## 6. 失败与边界

| 情况 | 处理 |
|---|---|
| `rules` 里有坏节点 / 未知 type / 未知 fact | 该条规则丢弃并记 warning，其余照常 |
| `target` 指向不存在的模式 | 跳过（每次 update 都按当前模式集合过滤，删模式不会留下死规则） |
| `id` 重复 / 缺失 | 缺失自动编号；重复保留第一条 |
| 进入与退出同一 tick 都成立 | 进入优先（下车立刻开枪不会被上一次退出拖住，沿用原设计） |
| 事实层没收到过任何扳机包 | 扳机事实全为假 → 规则不成立，不会误切 |
| 迁移：同 target 已有规则 | 不再补迁移规则，避免重复 |

## 14. 回填：叶子参数化（2026-11-29，第二条）

用户指出：叶子直接给「开车扳机」这种固定特征不够灵活，换个游戏没有这个特征怎么办。
改成按信号类型分：

- 叶子从 8 个固定事实收敛成 4 类：`trigger`（类型 + 参数前缀 + 作用侧，自定义类型码兜底）、
  `rumble`、`haptics`、`interact`；
- `SignalWatcher` 保留两侧原始扳机块，新增 `trigger_match(kind, code, prefix, side)`：
  先 `normalize_trigger_block`，再比类型码、比参数前缀（比的是第 1 字节起的参数部分）、
  按作用侧合并两侧结果；参数全零 = 没设效果，不算任何一种；
- 老 `fact` 节点在 `parse_condition` 里翻译，`parse_rules` 存**规范化后**的条件树，
  所以老规则集第一次被保存就升级成新写法（`normalize_condition` 有单测锁住）；
- 编辑面板：扳机叶子拆成「类型下拉 + 自定义码 + 前缀输入 + 作用侧下拉」，坏前缀只提示不改数据；
- GTA6 规则集改成「阻力 + `FF03` + 两侧」，行为不变；旧内置迁移表 `legacy_rules` 也改成新写法。

验证：**370 条单测全过**（原 345，净 +25）；弹窗冒烟把类型/码/前缀/侧逐个改一遍（含坏前缀）

## 15. 回填：规则收回预设 + 目标模式提到顶（2026-11-29，第三条）

用户两句话定了方向：**「自动切换应该和预设绑定，每个游戏不一样」**、
**「规则编辑没有编辑切到哪个模式」**。

  `rulesets/` 目录删掉，构建脚本里的 add-data 也删掉；
- 编辑面板去掉规则集那一栏，顶部改成 `预设「gta6」· N 条规则` + 同一个启用开关；

  直接提示「这个预设只有这一个非默认模式」；去抖移到它下面一行；

## 16. 回填：交互键 → 按钮叶子（2026-11-29，第四条）

用户的质疑很准：「交互键你怎么知道是哪个呢？」——原来是靠 `vehicle_key` 配置写死 `f`，
和按键预设里的「`f` → TRIANGLE」是两份独立的真相，改绑就静默失效，界面上还看不到这个字段。

改成**直接认手柄按钮**：

- 新叶子 `{"type":"button","name":"TRIANGLE"}`，可选名字与 `mapping.VALID_BUTTONS` 完全一致
  （加了一条单测守着两处不漂移）；
- 事实来源换成映射层的输出：`InputMapper.tick()` 的 `events` 里每个 `press` 都喂一句
  `SignalWatcher.note_button(按钮名)`——应用本来就要把这些事件发给主机，顺手一喂即可；
- 删掉 `AppConfig.vehicle_key`（配置、序列化、预设里的字段一起删），`note_interact` 也删掉；
- 旧规则里的 `interact` 叶子解析时翻译成「按钮 △」，写回就变成新格式；
- 编辑面板新增按钮下拉（△ / ✕ / ○ / □ / 十字 / L1… / 触摸板），换游戏照旧不用改代码。

顺带的好处：规则现在也能对其它按钮做判断（比如「冲刺 L3 时」「R1 开火时」）。

验证：**372 条单测全过**（新增按钮表对齐、按钮叶子解析、按钮脉冲窗口）；弹窗冒烟把

## 17. 回填：日志措辞、重画粒度、拖窗口（2026-11-29，第五条）

用户三条反馈：日志还在说「开车特征」；增删条件时界面要卡一下；窗口拖不动。

**1）日志措辞**。那句是规则引擎之前的诊断日志（`_note_pair_change`，logger 名还叫
`ps5kbm.vehicle`），用的是 GTA6 的固定说法，跟规则已经不共用同一套词。改成：

- logger 改名 `ps5kbm.trigger`，消息 `扳机信号：两侧无效果 Off → 两侧阻力 FF03（L=… R=…）`；
- `PAIR_LABELS` 只说信号（两侧有没有效果、类型码），不说「进车 / 步行」；
- 最近 8 帧原始扳机块从 INFO 降到 DEBUG —— 常态下每次变化只留一行，不再刷 8 行。

**2）重画粒度**。量出来的账（界面线程，都是用户能感觉到的卡顿）：

| 操作 | 改前 | 改后 |
|---|---|---|
| 规则面板整页重画 | 1140 ms | 645 ms |
| 加一个子条件 | ~1100 ms | 122 ms |
| 删一个子条件 | ~1100 ms | 244 ms |
| 改前缀 / 按钮 / 秒数 | ~1100 ms | ~0 ms |
| 映射列表重建（切模式触发） | 771 ms | 67 ms |

两处根因，各自对应一个改动：

- **`update_idletasks` 变成 O(n²)**：`CTkOptionMenu._draw()` 末尾每次都调
  `canvas.update_idletasks()`，一次重建几十个控件就等于把整棵界面排空几十遍
  （cProfile：3 次详情重画里 `update_idletasks` 占 2.1s）。customtkinter 6.0.0 没有
  延后 draw 的开关，所以加了 `ui_widgets.bulk_build(root)`：重建期间把
  `CTkCanvas.update_idletasks` 置空，结束统一排一次。模块里写清「官方没提供，只能这么绕」。
- **重建粒度太粗**：改一个前缀也要把 193 个控件全销毁重建。现在编辑面板记住
  「每个节点的子条件画在哪个容器里」（`app._rule_groups`），增 / 删 / 换类型只重画那一组
  （加子条件还能只追加一行），纯数据改动只刷新底部「读法」一行；
  映射列表在键位集合没变时**原地改文字**（`app._mapping_views`），不再整块重建。

**3）拖窗口**。用户确认只有「刚连上主机」时会这样，捕获中不拖。代码里唯一能造成
「拖着拖着弹回原位」的机制是**拖拽过程中改变激活窗口**：Windows 会取消整次拖动并把窗口
退回起点。覆盖层在捕获时每 800ms `focus_force()` 一次，正好会撞上。改成只在「前台确实是
别的程序」且「没有按着鼠标键」时才抢焦点（`windows.mouse_button_down()` /
`windows.foreground_is_ours()`），抢的时候记一行日志。

验证：372 条单测全过；`tools/bench_rules_refresh.py`、`tools/bench_ui_rebuilds.py` 给出上表；
`tools/smoke_rules_ui.py` 在真实界面里走一遍「加子条件 → 删子条件 → 换类型 → 改前缀 →
加规则 → 删规则 → 选中」，断言数据与画面行数一致。
